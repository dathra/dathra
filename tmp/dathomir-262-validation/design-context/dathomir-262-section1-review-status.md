## 1.1 コンポーネントの基本形【方向決定】

- サーバーの処理を `server`、SSR の構造定義を `template` とする。
- クライアント処理は別モジュールに置く。
- サーバーの初期化と `template` をブラウザで再実行しない。

## 1.2 クライアントの書き方【方向決定】

```ts
export default defineClient({ countText, increment });
```

- `bindings` / `operations` の区分を設けず、フラットに登録する。
- `template(values, { bind, on })` から対応するクライアントの型が付いた関数を受け取る。
- `bind` / `on` の両方で全登録名を補完候補とする。関数の役割で候補を絞り込まない。
- `?dathra-client` の独自 import 構文は使わない。
- 型の伝播と実行時のモジュール対応付けは 1.6 の方式を使う。

## 1.3 表示場所とサーバー内容【方向決定】

```ts
bind("countText", { server: `現在の値: ${values.count.value}` });
```

- `bind` はクライアントの結果を表示する場所のマーカー。
- `server` は実際に SSR で出力する内容。クライアント用のデフォルト値ではない。
- `kind` / `child` オプションは要求しない。
- 文字列から子 DOM、子 DOM から文字列への変更を許す方向。
- `creation` と別の表示宣言にせず、`bind` に統合する。

## 1.4 通常の一覧の識別【方向決定】

```ts
el("li", { _key: item.id }, txt(item.label));
```

- `_key` はランタイム用の情報とし、HTML 属性として出力しない。
- 同じ要素の DOM 保持や並べ替えに使う。
- `el()` は要素の記述を返し、実 DOM への反映はランタイムが行う。
- 記述の評価だけで実 DOM の生成やイベント登録を行わない。
- 通常の一覧では `keyed()` を使わない。
- 複数要素のまとまりと子固有の状態は 1.7 / 1.8 の未決事項。

## 1.5 接続直後の表示【方向決定】

- 状態の復元と接続が成功した後、クライアントの表示結果を一度自動反映する。
- 次のクリックや Signal の変更を待たない。
- 以降は Signal の変更に応じて更新する。
- 同じ表示に対する不要な DOM 変更を避け、異なる結果は宣言された範囲へ反映する。
- 接続失敗をクライアント側での再描画によって回避する設計にはしない。

## 1.6 戻り値とクライアントの対応付け【方向決定】

利用者レビューで採用した書き方:

```ts
import type CounterClient from "./counter.client.js";

const Counter = defineComponent({
  client: clientModule<typeof CounterClient>(
    "./counter.client.js",
    import.meta.url,
  ),
  server() {
    return { count: signal(7), title: "カウンター" };
  },
  template(values, { bind, on }) {
    // Component-specific typed helpers.
  },
});
```

- 通常の `@dathra/reactivity` の `signal` を使い、Signal と通常値を一つの戻り値にまとめる。
- 通常の値の入れ物は読み取り専用とし、Signal はブラウザ内に復元する。サーバーとメモリーを共有しない。
- `clientModule(specifier, import.meta.url)` は参照情報のみを作り、サーバーでクライアントモジュールを実行しない。
- TypeScript では default export の型を type import で渡す。型用と実行時用にパスを二度書くことは利用者が許容した。
- JavaScript では type import と型引数を省略し、同じ実行時参照を使う。配信には参照収集とマニフェストのビルド対応が必要。
- 型だけで実行時のパス一致や値の安全性が保証されるとは扱わない。

Sol の詳細案: `/tmp/dathomir-262-section1-return-and-client-link.md`。
仮の型定義を使った限定的な型チェックは成功。実際の復元、ビルド、DOM の動作は未検証。
Signal の正確な識別、入れ子と同一 Signal 参照の復元、snapshot の一貫性、型用と実行時用のパス検査は実装時の検証課題として残す。
Proposal 本文と実装はまだ変更しない。

## 1.7 複数要素をまとめる書き方【未決】

- 一つの項目が複数の DOM 要素からなる場合の表現。
- そのまとまりのどこに `_key` を指定するか。
- 不要な HTML ラッパーを追加せず表現する方法。

## 1.8 子ごとに状態を持たせる書き方【未決】

- 追加した行などが独自の Signal を持つ場合の宣言方法。
- SSR の状態を引き継ぐ場合と、ブラウザで新規作成する場合の区別。
- 再評価で状態を作り直さず保持するために、利用者が何を書くか。
- 1.6 の受け渡し契約と整合させて検討する。

- 接続後の更新が途中で失敗した場合の停止範囲と復旧方法。
- 型推論、値の復元、DOM 保持、接続後更新の実装検証。
